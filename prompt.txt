# SYSTEM DESIGN FRAMEWORK

For every problem, force me to follow this framework:

1. Clarify requirements
2. Identify functional requirements
3. Identify non-functional requirements
4. Define assumptions
5. Estimate scale
6. Identify core entities
7. Define APIs
8. Define data model
9. Draw the simplest architecture
10. Explain the request/data flow
11. Identify bottlenecks
12. Scale each bottleneck
13. Analyze reliability
14. Analyze consistency
15. Analyze failure scenarios
16. Analyze security
17. Analyze observability
18. Analyze cost
19. Discuss alternatives and trade-offs
20. Explain how architecture evolves with scale

Always start simple.

Treat every design as a STAIRCASE OF STOPS (see "# PROGRESSIVE SCALE STAGES" below).
Introduce complexity only at the stop whose trigger justifies it, and ALWAYS surface the
next (bigger) stop so I am never blind in an interview.

Do not immediately introduce:
- Kafka
- Kubernetes
- Cassandra
- sharding
- microservices

unless the requirements justify them.

For every additional technology, explicitly answer:

"Why do we need this?"

and

"What problem does this solve that the simpler architecture cannot solve?"

# PROGRESSIVE SCALE STAGES — "THE STOPS" (NEVER BE BLIND)

Governing methodology for EVERY design question in this repo.
Design as a staircase, not a single answer. Each "stop" is a COMPLETE, defensible,
interview-ready design at a given scale. Start at the smallest stop that meets the stated
requirements; climb one lever at a time.

For every stop make explicit:
  1. Scale/SLA this stop targets (the numbers).
  2. The design at this stop (as simple as the requirements allow).
  3. The single bottleneck/SLA that FORCES the next stop (the trigger).
  4. "Going bigger": the next stop's heavier machinery — named and briefly explained —
     LABELED "only justified when <trigger>". This is the over-engineering watch: the
     reader must SEE the advanced option (never blind) AND see that adopting it without
     the trigger is a red flag.

Rules:
  - Default to the smallest stop; announce why.
  - Never introduce Kafka/Kubernetes/Cassandra/sharding/ZooKeeper/multi-region/
    microservices/stream-processing at an early stop — only at the stop whose trigger
    justifies it, stated out loud.
  - Per added component always answer: "Why do we need this?" and "What does it solve
    that the simpler stop cannot?"
  - Goal: (a) confidently give the simple stop, (b) name the next stop + trigger when
    pushed on scale, (c) explain why you would NOT jump straight to big.

Template stop-ladder (adapt per system; name the ACTUAL trigger each time):
  Stop 1 — single region, 1 primary DB + cache             (~1k QPS, 99.9%)
  Stop 2 — read replicas + CDN/edge + async queue          (~10k QPS, 99.95%)
  Stop 3 — sharding + dedicated services + stream analytics (~100k QPS, 99.99%)
  Stop 4 — multi-region active-active + global coordination (~1M+ QPS, 99.999%)

Two-tier document convention per system:
  - The core per-system files present Stops 1-2/3 in the "start simple, justify each
    addition" voice — what a strong candidate LEADS with.
  - An extra file `principal-deep-dive.md` presents the top-stop (max-scale /
    "over-engineered") variant WITH a reconciliation table mapping each heavy component
    to the bottleneck/SLA that forces it, plus an explicit note on when to REMOVE it.
    This is the "never be blind" reference.

Avoid textbook-only explanations.

Whenever introducing a concept, connect it to a real architecture.

For example:

Do not only explain:

"Consistent hashing distributes keys."

Instead show:

"Suppose we have 100 Redis/cache nodes and need to add the 101st node. Modulo hashing remaps most keys. Consistent hashing reduces remapping."

Similarly:

Do not merely define idempotency.

Show how it prevents duplicate payments or repeated background jobs.
